# Pi Agent host

The app launches the packaged `Contents/Resources/ai/node` with `host.mjs`. API keys travel only in the private child stdin prompt frame and are cleared when the run settles. No coding-agent package, filesystem tool, shell tool, MCP loader, extension loader, credential environment variable, or persistent session backend is installed in the runtime.

Install using `pnpm install --frozen-lockfile --ignore-scripts`. Build using `node scripts/build.mjs`; test using `node --test test/*.test.mjs`. Package using `node scripts/package.mjs --arch arm64 --resources /absolute/App.app/Contents/Resources` (or x64). Node 22.23.3 archives are verified against SHA256 values from https://nodejs.org/dist/v22.23.3/SHASUMS256.txt. Sign the copied Node executable together with the app before distribution. Runtime minimum follows Node 22: macOS 11.0; x64 and signing/clean-machine operation require separate verification.

SDK: https://github.com/earendil-works/pi/tree/main/packages/agent and https://github.com/earendil-works/pi/tree/main/packages/ai. Versions are pinned to 1.2.0. Only the three relevant API implementations are bundled, rather than provider catalog entrypoints. The runtime never fetches models or switches providers automatically.

Protocol is JSON-lines UTF-8, version 1. Every frame has `sessionId`, positive monotonically increasing `generation`, `requestId`, `type`, `data`. Identifiers permit 1–96 ASCII letters, digits, underscore and hyphen. Individual frames are capped at 1 MiB, queued writes at 4 MiB, output at 4 MiB per run, structured context at 100 messages and 192 KiB UTF-8, tools at 128, pending tools at 32. Invalid input terminates the host. One prompt or model-discovery operation runs at once, at most 20 model turns per prompt. Provider SDK request retries are limited to two; streamed failures and tool writes are never replayed. The active-work run watchdog is three times the configured 5–300 second request timeout. A matching approvalWait frame pauses only this total watchdog while a tool is awaiting local approval; each provider request retains its independent network timeout. Cancellation remains active during approval.

`prompt.data`: `settings` (`provider`, `model`, optional `baseUrl`, `api`, `timeoutSeconds`, `maxTokens`, optional loopback-only `proxyUrl`), transient `key`, `user`, optional `context` (canonical SDK user/assistant/toolResult messages), legacy text `messages` (`role`: user|assistant; `content`: string), optional boolean `recoveryRequired`, and `tools` (`name`, `description`, JSON Schema `parameters`). Presets: glm-cn, glm-coding-cn, glm-global, glm-coding-global, kimi-cn, kimi-global, kimi-coding, deepseek, openai, anthropic, xai; plus custom.

Events: `text` with `text`; `status` with `status` and `turn`; `error` with sanitized `code`; `done` with `cancelled`, `failed`, and optional `taskStatus`; `context` with `messages` and `truncated`; `toolRequest` with separate tool `requestId`, `toolCallId`, `name`, `arguments`. Flutter replies with `toolResult`, using that tool requestId as envelope requestId and `data` containing `toolCallId`, `isError`, object `value`. Trusted Flutter commands own validation and approval. `cancel` and `close` use the active prompt identity. Old-session, old-generation and unmatched tool responses are discarded.

No live provider claims: six vendors require real API-key, streaming and structured-tool compatibility tests. GLM/Kimi billing endpoints remain separate. Custom HTTP permits loopback only; other endpoints require HTTPS without URL credentials or query parameters.

Proxy requests use a per-run Undici dispatcher, never global proxy environment state. Only loopback HTTP(S) proxy endpoints without credentials, query, fragment, or paths are accepted; model HTTP redirects are rejected. Flutter must check `AgentToolRequest.isCurrent()` after asynchronous approval and immediately before a command mutation. Prompt failures throw `AgentRuntimeException` and also emit sanitized error events. Event subscriptions are single-consumer; pausing cancels the active run to prevent unbounded consumer buffers.

Node 22.23.3 is selected over Node 24 because its official macOS deployment target is 11.0, preserving app compatibility: https://github.com/nodejs/node/blob/v22.23.3/BUILDING.md. Pi 1.2.0 and Undici 8.11.2 both require Node >=22.19.0.

`listModels.data` uses the same endpoint/proxy/timeout settings and transient `key`, without requiring `model`. It performs authenticated GET requests and emits `models` with a bounded list of `{id, name}`, followed by `done`; it never starts a conversation or tool test. Discovery has one configured request deadline, supports cancellation, rejects redirects, limits decoded response bytes to 512 KiB across all pages and models to 1000, and rejects malformed model identifiers. Anthropic pagination remains on the configured endpoint, with at most 20 pages and duplicate-cursor rejection.

Model discovery routes follow provider contracts: OpenAI, xAI and Moonshot use their configured `/v1/models`; DeepSeek uses `/models`; Claude uses `/v1/models` with `x-api-key` and `anthropic-version`; Kimi Coding uses `/coding/v1/models` with Bearer authentication. Custom connections use their selected OpenAI or Anthropic protocol. GLM endpoints have no documented list-model API in the current official API reference, so these presets explicitly return `modelsUnsupported` and support manual model IDs. An endpoint returning HTTP 404/405 is likewise reported as unsupported. Empty results, failure, timeout and unsupported discovery all retain manual entry. List retrieval makes no claim about chat, tool support or account eligibility.

References: [Claude model-list API](https://platform.claude.com/docs/en/api/models/list), [DeepSeek model-list API](https://api-docs.deepseek.com/api/list-models/), [xAI models API](https://docs.x.ai/developers/rest-api-reference/inference/models), [Moonshot model-list API](https://platform.moonshot.cn/docs/api/models), [Kimi Code provider configuration](https://moonshotai.github.io/kimi-cli/en/configuration/providers.html), [Z.ai API reference](https://docs.z.ai/api-reference/introduction).


The host keeps Pi Agent Core as the runtime and adds two local tools. `builtin_workflow_read({topic})` returns a bundled skill document for `local_rules`, `subscription_rules`, or `diagnostics`; the Markdown frontmatter and body are compiled into the bundle, with no filesystem lookup, external skill loader, or model-selected paths. Guidance defaults to Chinese, reads live catalogs before constructing arguments, permits conservative assumptions for reviewable drafts, and preserves native approval for application. Local rules use the independent `integration:flclash_local` target, can reuse existing node sets without an airport profile, and continue to the next ordered rule when matching candidates are empty. Subscription proxy groups and local node sets are distinct concepts.

Local-rule creation reads `policies_catalog` and `policies_read`, calls `policies_propose`, and ends at a real draft. To revise that uncommitted draft, read `policies_draft_read({id})` and pass its ID as `draftId` to `policies_propose`; never reconstruct the revision solely from the committed document. A request to preview a draft does not authorize committing or changing the active network configuration.

`task_finish({status,summary,proposalId?,operationId?,reason?})` declares `draft_ready`, `completed`, `needs_input`, `failed`, or `chat`. The SDK automatically binds draft and completion outcomes to the latest actual application-tool result after the last mutation; the model need not know provider-assigned tool call IDs. Optional `proposalId`/`operationId` select a resource ID visible in real tool output; legacy `evidenceToolCallIds` remain compatible. Outcomes require actual results from the current run; invented call IDs, stale success before a later failed mutation, and pending/queued/accepted results cannot prove completion. A saved proposal with an ID supports `draft_ready`, while a successful terminal result supports `completed`. Blocking outcomes require a concrete reason. An accepted finish ends the run and its summary is emitted as visible text if the model has not already emitted it; `done.taskStatus` carries the accepted status. Read-only queries and diagnostics use `chat` or a direct answer; `chat` cannot close a run with an actual mutation. Ordinary chat and necessary clarification questions may finish normally. If a tool-proven mutation/draft has no task outcome and the model stops without a question, at most two context-only correction turns ask it to finish accurately. Read-only status results do not trigger correction, and the host never replays a tool write.

When `context` is present it replaces legacy text history rather than being appended to it. Only user text, assistant text/toolCall blocks, and paired toolResult text are accepted; system messages and unmatched call/result pairs are rejected. Tool call IDs share the application's 200-character limit. The host rebuilds safe assistant model metadata and zero usage, drops thinking, signatures, provider diagnostics, raw error messages, and tool details, and emits canonical context before `done`, including after errors/cancellation. Completed tools remain paired; an unfinished call is omitted unless the SDK recorded its error result. Input keys are removed from exported string values; Flutter remains responsible for recursive credential/URL redaction and safe persistence. The context is the complete retained transcript, not a delta. Resume it without replaying its tool calls as new application actions.

Context retention keeps the most recent complete user rounds under 192 KiB and 100 messages. Oversized tool-result text is condensed to actual safe status, ID, operation ID, proposal ID, and error-code evidence with `contextTruncated: true`, rather than dropping executed-write evidence. A newest round that still exceeds the bound causes `contextLimit`; callers must treat that as incomplete context rather than silently resuming an older transcript. Structured application-tool errors retain their JSON payload and safe machine `code`, along with `isError: true`, instead of becoming an opaque `commandFailed` string.

Flutter sends `approvalWait` with the active prompt requestId and `data: {pending: true|false}`. Only the current session/generation/prompt can change the timer, and pausing requires a pending tool request. Returning the last pending tool result automatically resumes the remaining active-work budget. Old identities are ignored. Local approval is neither a network retry nor a provider request; it does not consume the total active-work timeout.

The host workflow tests run without real API credentials: mock tool chains cover draft creation/revision, genuine completion checks, cancellation evidence, structured failures without write replay, provider retry options, context bounds, ordinary chat/clarification, and virtual-clock approval waits. Provider adapter tests use isolated local mock endpoints; no live model capability or billing claim follows from these checks.


`prompt.data.recoveryRequired: true` adds a trusted instruction that the previous run was interrupted or its context is incomplete. The model must inspect actual state, saved drafts, and operation outcomes before continuing and must not replay writes on the assumption that interruption meant failure. Flutter owns persisting and clearing this recovery marker; the host validates it as an optional boolean and does not infer application state from it.

Local-rule revision guidance sends only requested fields: renaming uses `id`/`label`, changing the node set uses `id`/`choices`, and `priority` is included only when the user explicitly changes ordering. Common initial drafts contain 3–5 simple routing rules and do not add unsolicited features such as ad blocking. All user-visible prose is Chinese; the finish summary is shown once as the final result.
